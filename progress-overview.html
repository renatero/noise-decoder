Noise Decoder · implementation overview

From visible posts to explainable network evidence

A current overview of the browser extension, Coordination Radar dashboard and API, public-source collection, evidence pipeline, statistical model, deployment, and limitations.

Chrome Manifest V3 JavaScript feature pipeline Python + NetworkX engine Evidence for review, not intent attribution

Executive summary

Noise Decoder now has two ways to create an investigation: the Chrome extension extracts posts visible on a page after a user action, while the Coordination Radar web dashboard searches supported public sources through its FastAPI service. Both paths produce normalized records for inspection and analysis. The analysis looks for exact canonical URL reuse and near-duplicate text, groups related posts, checks for activity bursts, records recurring account-pair co-activity, builds a weighted actor graph, estimates a max-cluster permutation p-value, and discovers actor communities in Python.

The implementation keeps observable evidence distinct from conclusions. A shared link, similar message, synchronized burst, community membership, rhetorical cue, edge weight, or heuristic score does not by itself show deception or coordination. The system preserves examples and method details so a person can inspect why a relationship was surfaced.

Deployment status (15 November 2026): commit 619ad66 is deployed from r-dev to 2.24.173.100. The coordination-radar service is active behind Nginx at decodethenoise.today; HTTPS is enabled with a renewing Let's Encrypt certificate.

The VPS keeps the original Noise Decoder extension API on loopback port 8000 and runs the Coordination Radar dashboard API on loopback port 8001. Nginx terminates TLS, redirects HTTP to HTTPS, routes dashboard traffic to port 8001, and preserves the original API endpoints on port 8000. The Chrome extension defaults to the HTTPS domain.

Possible propaganda-technique cues

Reports compare post text with transparent lexical cues for the 18 labels in the PTC taxonomy, including loaded language, name calling, repetition, fear appeals, whataboutism, and straw men. Each candidate lists the matched words or phrase, its character offsets in the original event text, supporting posts and accounts, and low confidence. The taxonomy follows Da San Martino et al., Fine-Grained Analysis of Propaganda in News Articles; this implementation is not their trained model and a match requires human review.

One distinct cue adds 5% to the network-only heuristic score only when it appears in posts by at least two accounts in an already repeated-evidence community. The uplift is capped at 25%. Reports preserve network_heuristic_suspicion_score and place the adjusted value in heuristic_suspicion_score. The permutation p-value still tests the network-only score. Context.dev article cues are reported separately and never change the account-network score.

Coordination Radar dashboard and API

The dashboard is served by the same FastAPI application that collects sources and analyzes normalized events. It offers reproducible synthetic coordinated and benign scenarios, bounded live searches, an offline Bluesky snapshot, and normalized JSON import. Reports show the sources searched, query, completion state, result counts, and source errors, including when a search returns no usable records. Failed sources are reported as unknown coverage rather than as zero matches; partial results from healthy sources are retained.

The dashboard analysis adapter canonicalizes submitted URLs and forms shared-URL groups. An account pair is treated as a recurring relationship only when it co-occurs in at least two distinct URL groups; single-context edges remain visible as limited evidence. It passes the evidence-weighted graph into the Python community engine. This API path is deliberately narrower than the extension payload, which also carries text-similarity matches, rolling time-window bursts, and the stratified permutation report. News articles tagged news_context are returned as background context and never treated as account evidence.

Bluesky and combined collection are bounded and unauthenticated. Public-feed searches inspect current headlines and summaries; they are not publisher archives. Live collection responses preserve source attribution and coverage diagnostics for display and report export.

Context.dev requires a server-side CONTEXT_API_KEY. Its collector defaults to 20 new upstream requests per UTC day and allows at most four new requests per minute; each request fetches at most 10 candidates. Ten-minute cache hits do not consume credits. Searches require the dashboard request header and reject foreign browser origins. If the key is not configured, the dashboard marks this source unavailable and other sources remain usable.

On the VPS, Nginx serves the dashboard over HTTPS and proxies it to the app bound at 127.0.0.1:8001; the original extension API remains at 127.0.0.1:8000. The app's /healthz route was checked after deploying commit 619ad66.

The analysis pipeline

  1. User-initiated extractionThe Manifest V3 popup injects a self-contained extractor only after the user selects “Extract visible posts.” It reads visible article-like items from the active web page.
  2. Normalization and feature extractionMessage text is normalized and tokenized; post and outgoing URLs are canonicalized; the batch is compared for shared links and near-duplicate wording.
  3. Related-content groupsPosts connected by shared canonical URLs or high token overlap form connected components with pairwise evidence.
  4. Time-window burstsRelated posts are scanned in rolling windows, counting distinct identified accounts and retaining invalid-timestamp diagnostics.
  5. Repeated co-activityAccount pairs are tracked across distinct content groups and detected bursts. Single-context patterns remain limited evidence.
  6. Weighted actor graph and permutation nullAccounts become nodes, recurring pairs become weighted edges, and a stratified randomization compares the strongest discovered actor cluster with a simulated maximum-score distribution.
  7. Network communitiesThe Python engine uses NetworkX greedy modularity on the repeated-edge graph and returns community summaries and representative examples.

Collection, normalization, and matching

Collection behavior

The extension has no always-running page collector. Collection begins after a user action. Extraction uses common article/feed selectors and a small set of platform-oriented selectors; real page markup is dynamic, so results are deliberately incomplete and should be reviewed before submission.

Text features

The feature module removes zero-width characters, applies Unicode NFKC normalization, collapses whitespace, and lowercases text. Unicode-aware tokenization retains letters and numbers. Similarity uses Jaccard overlap on token sets; candidate pairs are generated through an inverted token index rather than a full all-pairs scan. A text pair qualifies at Jaccard similarity of at least 0.8, with at least three unique tokens on each side.

URL features

HTTP(S) URLs are canonicalized by dropping fragments and common tracking parameters, lowercasing the host, removing default ports and trailing path slashes, and sorting remaining query parameters. Exact canonical outgoing URL matches are recorded separately from text similarity. This makes common tracking variants comparable while retaining non-tracking query values.

Extracted events preserve the visible text and include normalized text, tokens, canonical permalink, canonical outgoing links, shared-URL evidence, and near-duplicate matches.

Groups, bursts, and recurring co-activity

Related-post groups

Pairwise edges are created for qualifying token similarity or exact canonical outgoing URL matches. Connected components become content groups. Each group includes post IDs and the pairwise match reasons, similarity values, and shared URLs that connect its members.

Rolling publication windows

The extension settings page exposes a rolling window from 1 to 10,080 minutes (default 60) and a minimum of 2 to 100 distinct accounts (default 2). Within each related-content group, posts are sorted by publication time. A burst is reported when the configured number of identified accounts appears within the interval. Missing or invalid publication timestamps are excluded and counted. Posts with unknown account IDs can contribute to post counts but not to the distinct-account threshold.

Repeated account-pair co-activity

For each account pair, the extension records the distinct content groups and publication bursts where both accounts appeared, their contributed post IDs, and direct pairwise evidence when available. A pair is marked repeated if it appears in at least two content groups or at least two bursts. One group plus a burst derived from that group does not count as repetition.

The output also includes an evidence assessment. A pair supported only within one content group is labeled limited, even when it recurs across multiple bursts in that group. The report explicitly says that a common cause such as a breaking-news event may explain simultaneous activity. The system does not independently detect breaking news.

Weighted actor graph

The extension constructs an undirected graph. Identified accounts are nodes with observed platforms, posts, content-group IDs, and burst IDs. Account pairs are edges with their recurrence counts and supporting context records. Unknown IDs are excluded from this graph so multiple unidentified posts are not collapsed into one artificial account.

These weights are transparent evidence-support scores. They are not probabilities, confidence levels, or findings of intent.

Permutation null model and strongest-cluster test

The current statistical comparison runs 199 actor-assignment permutations. Post content, URL, timestamp, platform, and group membership remain fixed. Actor labels are shuffled among identified posts sharing the same platform, a coarse topic proxy (the most common non-stopword token in the extracted batch), and an epoch-aligned UTC time bucket sized by the configured window. Actor counts within each stratum are preserved.

For the observed data and for every permutation, the procedure discovers connected components using repeated actor-pair edges and selects the candidate with the largest sum of edge weights. The p-value compares the observed strongest candidate against the distribution of simulated maximum cluster scores. This max-statistic approach is intended to account for searching across candidate clusters rather than presenting thousands of uncorrected pairwise p-values.

Score and statistical comparison: network_heuristic_suspicion_score is the pre-adjustment network support. heuristic_suspicion_score applies the bounded rhetorical-cue uplift and remains uncalibrated; it is not a probability. permutation_p_value compares the network-only score using the upper-tail plus-one formula: (1 + simulated maxima ≥ observed maximum) / (permutations + 1).

With 199 permutations, p-values have a minimum and step size of 0.005. That is enough to demonstrate the null comparison and flag broad departures from the simulated baseline; it is too coarse for fine-grained ranking or strong inferential claims. Results also include a random seed, null mean and spread, 95th percentile, exceedance count, and stratum diagnostics. The p-value is null when there is no observed candidate, no shuffleable stratum, or no variation in the maximum statistic.

The topic proxy is approximate, and actor-pair multiple-testing adjustments are not separately reported. These limitations should accompany interpretation.

NetworkX community discovery

The Python engine accepts the extension payload and builds a NetworkX undirected graph from repeated evidence-weighted actor edges. One-off edges remain in the raw actor graph but do not join the community-discovery graph. Connected components are partitioned with NetworkX greedy modularity using edge weight values.

Each returned community includes:

  • cluster size and member account IDs;
  • counts of distinct repeated content-group and burst contexts;
  • participating platforms;
  • summed weighted support and partition modularity;
  • representative examples with post IDs, excerpts, timestamps, URLs, and matching evidence;
  • a plain-language explanation.

Explanations use measurable language, for example: “3 accounts formed a repeated-evidence network, sharing 4 distinct canonical URLs, across 3 content groups, with 3 detected publication bursts lasting up to 60 seconds.” The engine says “distinct,” not “unrelated,” because semantic independence of URLs is not established by URL matching. It carries the permutation p-value separately from heuristic support scores.

Payload and local workflow

The extension review and its legacy API request carry extracted events plus clusters, time_window_analysis, co_activity, actor_graph, and permutation_analysis. The dashboard API instead accepts normalized events at POST /api/analyze, applies its shared-URL evidence adapter, and returns report status, summary, graph, clusters, statistics, evidence, and limitations. The engine’s analyze(payload) function returns community and statistical details for the extension payload.

A synthetic editable request is kept at the repository root as payload.json. It is in .gitignore, so it stays local and is not included in future commits. It contains three sample accounts across three content groups and bursts. Replace its fields with a reviewed payload to try the engine.

Install the Chrome extension locally

The extension is loaded directly from this repository in Chrome. It opens the Noise Decoder dashboard for a selected phrase, link, or page; it does not collect page content by itself.

  1. Clone or download the Noise Decoder repository and unpack the files if needed.
  2. Open chrome://extensions in Chrome and turn on Developer mode.
  3. Select Load unpacked and choose the repository's chrome-extension folder.
  4. Open the extension's options to confirm the dashboard address is https://decodethenoise.today/dashboard.

On a page, select text or right-click a link or the page, then choose Investigate with Noise Decoder. The extension opens the dashboard with that reference; opening it does not mean the content has been collected or analyzed.

Validation coverage and current limits

The JavaScript extension suite covers text normalization, URL canonicalization, grouping, rolling-window boundaries, invalid timestamps and account IDs, co-activity repetition, weighted graph scores, and max-cluster permutation behavior. Dashboard checks cover source coverage display and report feedback.

Python coverage spans the API routes and error behavior, source collectors, Context.dev request budgeting and caching, the normalized-event integration adapter, NetworkX communities, evidence summaries, p-value separation, malformed input, a repeated synthetic campaign, and a one-off viral-news negative example. The viral example has no repeated edges and does not form a community; the system does not automatically label it deceptive.

  • Visible extraction depends on changing public-page markup and may miss or misread posts.
  • Some actor IDs are built from visible display names; these may not uniquely identify an account.
  • Canonical URL equality is a sharing signal, not a statement that the linked material is independent or coordinated.
  • Timing and similar text can arise from common external causes; the breaking-news caution is explicit, but breaking news is not classified by the software.
  • Greedy modularity is a heuristic partition, especially uncertain on small or sparse graphs.
  • The permutation topic proxy is coarse and 199 runs provide limited p-value resolution; the results demonstrate a method rather than establish intent.
  • The VPS now has HTTPS through Let's Encrypt, but application authentication and operational monitoring are not included.
